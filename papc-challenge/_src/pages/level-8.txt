### A correct optimiser never changes an answer

::: box Definition 8.1 (Correct optimiser)
An *optimiser* is a function $\mathit{opt}$ from queries to queries. It is *correct* if $\lBrack \mathit{opt}(q) \rBrack = \lBrack q \rBrack$ for every query $q$ and every database (Definition 5F.4).
:::

- To prove it: induction on $q$, one case for each operator, as on lists in Levels 5T and 6.
- In each case, the rewrite is one of the laws of [[7]], and the law's side condition is exactly what $\mathit{opt}$ must check before it rewrites.

### A first optimiser: merge selections

Start small: an optimiser that only merges a selection into the selection below it, by law 1.

::: box Definition 8.2 (Merging selections)
$$\begin{aligned}
\mathit{merge}_p(\sel{q}(r)) &= \sel{p \wedge q}(r) \\
\mathit{merge}_p(r) &= \sel{p}(r) && \text{if } r \text{ is not a selection} \\
\mathit{opt}(\sel{p}(q)) &= \mathit{merge}_p(\mathit{opt}(q)) \\
\mathit{opt}(q_1 \cup q_2) &= \mathit{opt}(q_1) \cup \mathit{opt}(q_2) && \text{and the same for } -,\ \times,\ \pi_A,\ \rho_{a \to b} \\
\mathit{opt}(T) &= T
\end{aligned}$$
:::

::: box Fact 8.3
$\lBrack \mathit{merge}_p(r) \rBrack = \lBrack \sel{p}(r) \rBrack$, for every query $r$.
:::

::: proof
If $r = \sel{q}(r')$: $\lBrack \sel{p \wedge q}(r') \rBrack = \sel{p \wedge q}(\lBrack r' \rBrack) = \sel{p}(\sel{q}(\lBrack r' \rBrack)) = \lBrack \sel{p}(\sel{q}(r')) \rBrack$, by law 1 in the middle. Otherwise, the two sides are the same query.
:::

::: box Theorem 8.4
$\mathit{opt}$ is correct.
:::

::: proof
By induction on $q$. For a name $T$, $\mathit{opt}(T) = T$. For $\sel{p}(q)$:
$$\lBrack \mathit{opt}(\sel{p}(q)) \rBrack = \lBrack \mathit{merge}_p(\mathit{opt}(q)) \rBrack = \sel{p}(\lBrack \mathit{opt}(q) \rBrack) = \sel{p}(\lBrack q \rBrack) = \lBrack \sel{p}(q) \rBrack,$$
by Fact 8.3, then the induction hypothesis. Every other operator: the induction hypotheses for its parts, and Definition 5F.4.
:::

### Moving selections down, side conditions checked

The next optimiser moves a selection through a product, by law 5, whenever its side condition holds:

$$\mathit{opt}(\sel{p}(q_1 \times q_2)) = \sel{p}(\mathit{opt}(q_1)) \times \mathit{opt}(q_2) \quad \text{if } \mathit{attrs}(p) \subseteq \mathit{schema}(q_1).$$

The check $\mathit{attrs}(p) \subseteq \mathit{schema}(q_1)$ is computed, by the program, on the query; in the proof, it is exactly the hypothesis that law 5 needs. If the check fails, the optimiser leaves the query as it is, which is always correct.

### Questions

::: q 8.A The laziest optimiser
Is $\mathit{opt}(q) = q$ a correct optimiser?

::: answer
Yes: $\lBrack q \rBrack = \lBrack q \rBrack$. It is correct, but it does nothing useful. Correctness says that the answer never changes; it says nothing about speed. Proving an optimiser *faster* needs a cost model: a stretch goal.
:::
:::

::: q 8.B A rewrite without its check
What goes wrong if $\mathit{opt}$ moves $\sel{\att{topic} = \val{Lists}}$ onto $\rel{Member}$ in $\sel{\att{topic} = \val{Lists}}(\rel{Member} \times \rel{Session})$?

::: answer
$\rel{Member}$ has no $\att{topic}$, so $\sel{\att{topic} = \val{Lists}}(\rel{Member})$ breaks the schema rule of selection. In a typed design it cannot be written; in the simpler design of [[5f]] it keeps no row (no row has a topic to compare), and the answer becomes empty, which is wrong.
:::
:::

::: q 8.C Run the first optimiser
Compute $\mathit{opt}(\sel{p}(\sel{q}(\sel{r}(T))))$.

::: answer
$\mathit{opt}(\sel{r}(T)) = \mathit{merge}_r(T) = \sel{r}(T)$; then $\mathit{opt}(\sel{q}(\sel{r}(T))) = \mathit{merge}_q(\sel{r}(T)) = \sel{q \wedge r}(T)$; and finally $\sel{p \wedge (q \wedge r)}(T)$. All three selections are merged, because $\mathit{opt}$ works from the bottom up.
:::
:::

::: q 8.D Why does it terminate?
Why does $\mathit{opt}$ always terminate?

::: answer
It calls itself only on the parts of its argument ($q$, $q_1$, $q_2$), which are smaller terms, and $\mathit{merge}_p$ does not call $\mathit{opt}$ at all: the recursion is *structural*. An optimiser that rewrites and then calls itself again on the result, until nothing changes, is not structural, and needs a termination proof ([@tpil-wf]).
:::
:::

::: part lean A correct optimiser

### Definition 8.1 in Lean is one theorem

```lean goal.lean (sketch)
-- The optimiser never changes an answer
theorem optimise_correct (db : Database) (q : Query) :
    eval db (optimise q) = eval db q := by sorry
```

Prove it by induction on `q`, using your laws of [[7]]. With the simpler design of [[5f]], `eval` computes lists, and law 1 holds even as lists (Fact 5T.4): the first optimiser needs no finite sets.

### A first optimiser, in Lean

```lean optimise.lean
-- Definition 8.2, for the simpler design of Level 5F
def mergeSel (c : Cond) : Query → Query
  | .select d q => .select (.and c d) q
  | q => .select c q

def optimise : Query → Query
  | .table n => .table n
  | .select c q => mergeSel c (optimise q)
  | .project attrs q => .project attrs (optimise q)
  | .rename a b q => .rename a b (optimise q)
  | .union q r => .union (optimise q) (optimise r)
  | .diff q r => .diff (optimise q) (optimise r)
  | .product q r => .product (optimise q) (optimise r)
```

The second case of `mergeSel` applies only when the first does not: Lean tries the cases in order.
